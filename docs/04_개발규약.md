# BookSummaryApp 개발 규약

작성일: 2026-09-20
상태: 초안
관련 문서: [01_기획.md](01_기획.md)

무엇을 만들지는 기획 문서에서 다루고, 이 문서는 어떻게 작업할지를 다룬다.
공개 저장소로 운영하므로 후반에 추가하면 비용이 크거나 복구가
불가능한 항목을 초기부터 유지한다.

## 1. 품질 기준

| 항목 | 기준 |
|---|---|
| 커밋 히스토리 | 프로젝트 시작 시점부터 기능 단위 커밋. 의미 있는 메시지 유지 |
| 사전 검사 | 커밋 전 포맷·정적 분석 통과. 빌드가 깨진 커밋을 남기지 않음 |
| README | 해결 과제, 아키텍처 구성도, 기술 선택 근거, 실행 방법, 화면 캡처 |
| 테스트 코드 | 핵심 로직 한정 — LLM 응답 파싱, OCR 실패 판정, 문항 수 산정 |
| 예외 처리 | 네트워크 실패, 타임아웃, 빈 상태, OCR 실패 분기 구현 |
| 배포 | Docker 기반 구성 유지. 배포 자체는 후반 과제 |

커밋 히스토리는 나중에 고칠 수 없다. 예외 처리와 빈 상태 누락은 공개 시
가장 먼저 드러나는 부분이다.

### 브랜치

- 기본 브랜치: `main`
- 기능 브랜치: `feature/{기능명}`에서 작업 후 `main`으로 병합
- 혼자 작업하므로 PR은 강제하지 않되, 단위가 큰 변경은 PR로 남겨 기록을 만든다

### 커밋 메시지

```
{타입}({스코프}): {요약}
```

타입·스코프 목록, 제목·본문 작성 기준, 커밋 단위는
[.ai/rules/git.md](../.ai/rules/git.md)를 따른다.

API 스펙 변경은 두 저장소에 걸치므로, 양쪽 커밋 메시지에 같은 요약을 남겨
나중에 짝을 찾을 수 있게 한다.

## 3. 문서 관리

### 위치 원칙

기획 문서는 프로젝트 전체를 대상으로 하므로 앱 저장소의 `docs/`에 단일 보관한다.
서버 저장소는 README에서 링크로 참조한다.

```
BookSummaryApp/docs/
├── 01_기획.md        개요, 확정 스펙, 데이터 모델, LLM 스키마, 저장소 구성
├── 02_화면흐름.md     화면 상세, 전이, 공통 규칙
├── 03_API명세.md      엔드포인트, 요청·응답, 에러 코드
├── 04_개발규약.md     본 문서
└── 기획서.html        01~03 통합 열람용
```

### 역할 경계

| 문서 | 담는 것 | 담지 않는 것 |
|---|---|---|
| 01 기획 | 무엇을 만들지, 확정 스펙, 설계 결정과 근거 | 작업 방식, 코드 규약 |
| 02 화면흐름 | 화면 구성, 사용자 액션, 예외 분기 | 레이아웃 수치, API 상세 |
| 03 API명세 | 엔드포인트 계약, 스키마, 에러 | 화면 동작, 구현 코드 |
| 04 개발규약 | 작업 방식, 품질 기준, 구조 규칙 | 제품 스펙 |

실측 후 조정할 값은 01 문서 8장에서 일괄 관리한다. 같은 값을 여러 문서에
적지 않고, 필요하면 링크로 참조한다.

### 기획서 HTML

`기획서.html`은 01~03을 열람용으로 합친 파일이다. 원본은 마크다운이며
HTML은 수동 재생성한다. 마크다운을 고친 뒤 HTML을 갱신한다.

## 4. README 구성

양쪽 README는 상호 링크를 유지해 한쪽만 방문한 경우에도 다른 구성 요소의
존재를 인지할 수 있게 한다.

### 앱 저장소

1. 한 줄 소개와 화면 캡처 또는 GIF
2. 해결하려는 과제
3. 아키텍처 구성도 — 앱 내 OCR부터 서버 응답까지
4. 기술 선택 근거 (01 문서 10장 내용을 옮겨 서술)
5. 개발 방식 — AI 도구를 어떤 작업에 활용했는지 기술한다
6. 실행 방법
7. 서버 저장소 링크

커밋에는 공동 저자 푸터를 넣지 않는 대신 README에 명시한다. 표기 위치를
옮기는 것이며 사실을 감추지 않는다.

### 서버 저장소

1. 한 줄 소개
2. API 요약 표 — 상세는 03 문서 링크
3. 실행 방법 (로컬, Docker)
4. 환경 변수 목록
5. 배포 구성
6. 앱 저장소 링크

## 5. 코드 구조

### 앱 (Flutter)

기능별 3계층. UseCase 계층은 두지 않는다.

```
lib/
├── core/            network, error, theme, router
├── features/
│   ├── library/     홈(책 목록), 책 상세
│   ├── capture/     촬영, OCR, 텍스트 확인, 책 선택
│   ├── summary/     요약 생성 대기, 요약 보기
│   └── quiz/        퀴즈 풀이, 채점 결과
└── main.dart

features/{name}/
├── data/            DTO, repository 구현
├── domain/          model, repository 인터페이스
└── presentation/    screen, widget, provider
```

의존 방향은 `presentation → domain ← data`다. `presentation`은 `data`를 직접
참조하지 않으며, `domain`은 Flutter 의존성을 갖지 않는다.

상태 관리는 Riverpod을 쓰고 비동기 상태는 `AsyncValue`로 다룬다. 로딩·에러
상태를 직접 정의하지 않는다.

화면 파일명은 화면 흐름 문서의 식별자와 대응시켜 추적 가능하게 한다.

### 서버 (Spring Boot)

```
src/main/kotlin/com/boohs/booksummary/
├── controller/      HTTP 경계
├── service/         유스케이스, 트랜잭션 경계
├── repository/      데이터 접근
├── domain/          엔티티
├── dto/             요청·응답
├── llm/             LlmClient(포트), GeminiClient(어댑터), prompt, validator
├── config/
└── common/          예외, 에러 코드
```

LLM만 인터페이스 뒤로 분리한다. 교체 가능성이 실재하고 테스트에 대역이
필요한 유일한 지점이기 때문이다. 나머지는 추상화하지 않는다.

## 6. 네이밍

| 대상 | 규칙 |
|---|---|
| API 필드 | camelCase (`documentId`, `keyPoints`) |
| API 경로 | 복수형 명사 (`/documents`, `/quizzes`) |
| Kotlin | 표준 컨벤션. 클래스 PascalCase, 함수·변수 camelCase |
| Dart | 표준 컨벤션. 파일명 snake_case |
| 식별자 | 접두사 + ULID (`doc_`, `quz_`, `job_`, `res_`) |
| 상태 상수 | 대문자 스네이크 (`PROCESSING`, `DONE`, `FAILED`) |

## 8. 환경 변수

| 이름 | 용도 |
|---|---|
| `LLM_API_KEY` | LLM API 인증 키 |
| `LLM_MODEL` | 사용 모델 식별자 |
| `FIREBASE_PROJECT_ID` | 토큰 검증용 프로젝트 식별자 |
| `DB_URL` / `DB_USER` / `DB_PASSWORD` | 데이터베이스 접속 |

키는 저장소에 커밋하지 않는다. 로컬은 `.env`, 배포는 플랫폼 환경 변수를 사용하고
`.env.example`에 이름만 남긴다.

## 9. AI 작업 환경

저장소마다 동일한 구조를 둔다. `AGENTS.md`를 Claude Code와 Codex의 공통
진입점으로 두고, `CLAUDE.md`는 별도 내용 없이 `AGENTS.md`를 가리키는 심볼릭
링크로 유지한다. 기능 작업 전 해당 규칙 문서를 읽는다.

```
{저장소}/
├── AGENTS.md              진입점. 한 줄 소개 + 규칙 링크 + 금지 사항
├── CLAUDE.md -> AGENTS.md
├── .ai/
│   ├── rules/             작업 규칙
│   └── context/           도메인 용어, API 계약 요약
└── .claude/
    ├── skills/            반복 작업 자동화
    └── settings.json      허용 명령
```

| 파일 | 앱 | 서버 |
|---|---|---|
| `rules/architecture.md` | 3계층 구조, 의존 방향 | 레이어드, LLM 경계 |
| `rules/coding.md` | 위젯, 상태 관리 | Spring, DTO, 식별자 |
| `rules/git.md` | 공통 (복사 보관) | 공통 (복사 보관) |
| `rules/testing.md` | 공통 (복사 보관) | 공통 (복사 보관) |
| `rules/docs.md` | 문서 톤과 갱신 규칙 | — |
| `context/domain.md` | 공통 (복사 보관) | 공통 (복사 보관) |
| `context/api-contract.md` | 엔드포인트 요약 | 엔드포인트 요약 |

`AGENTS.md`는 짧게 유지한다. 매 세션 컨텍스트에 포함되므로 상세 내용은
규칙 파일로 내리고 링크만 둔다.

공통 규칙은 저장소가 분리되어 링크로 참조할 수 없으므로 복사해 보관한다.
한쪽을 고치면 다른 쪽도 함께 고친다.
