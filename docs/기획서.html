01핵심 흐름

이미지는 서버로 전송하지 않는다. OCR은 기기에서 처리하고 서버는 텍스트만 받는다.

  └─ 책 선택 → 책 상세(회차 목록)      │
                └─ [회차 추가] ────────┤
                                       ▼

   ↓

   ↓

   ↓

   ↓

책 > 회차 두 단계. 한 권을 여러 번에 나눠 촬영하게 되므로 평면 목록으로는 권 구분과 진도 파악이 불가능하다. 책 상세에서 시작하면 대상 책이 이미 정해져 있으므로 책 선택 단계를 건너뛴다.

이미지를 서버에 보내지 않는 구조가 저작권 부담, 서버 부하, 업로드 대기를 동시에 줄인다. 대신 OCR 품질이 기기 성능에 좌우되므로 텍스트 확인 화면을 안전장치로 둔다.

저작권 처리

촬영 이미지는 서버로 전송하지 않으며 저장하지 않는다. 추출 텍스트는 개인 학습 목적으로만 보관하고, 공유·배포 기능은 제공하지 않는다. LLM 무료 티어는 입력 데이터가 모델 개선에 활용될 수 있으므로 용도를 개인 학습으로 한정한다.

03분량 연동 규칙

확장 시 요약 핵심 항목 수와 퀴즈 문항 수를 1:1로 맞춘다. 기준은 장수가 아니라 글자 수다.

서버가 글자 수로 목표 핵심 항목 수를 산정해 요약 프롬프트에 전달하고, 생성된 핵심 항목 개수를 그대로 문항 수로 사용한다.

텍스트 길이핵심 항목퀴즈 문항
~1,500자33
1,500~4,000자44
4,000~7,000자55
7,000자~66

1:1 대응. 요약과 퀴즈가 대응해 학습 점검 도구로 기능하며, 출제 범위가 문서 전체에 고르게 분포한다.

상한 6. 출력 토큰과 풀이 시간을 제한한다.

1차 구현은 3문제 고정. 요약 품질이 안정된 뒤 연동 방식으로 확장한다.

응답 검증

문항 수는 서버에서 계산해 프롬프트에 숫자로 전달하고, 구조화 출력 스키마에서 배열 길이를 강제한다. 실제 개수가 요청과 다르면 부족 시 재요청, 초과 시 절단한다. 검증 실패 시 1회 재요청하고, 재차 실패하면 LLM_INVALID_RESPONSE로 작업을 종료한다.

핵심 항목의 type이 정의된 여섯 값에 해당하지 않으면 definition으로 치환한다. LLM이 스키마에 없는 값을 생성할 수 있으므로 서버에서 방어한다.

04화면 흐름

화면 10개. S1 책 목록 → S2 회차 목록 → S8 요약 보기의 3단 구조이며, S8이 회차의 허브 역할을 한다.

S1

홈 · 책 목록

책 카드 목록. 제목, 회차 수, 마지막 학습일, 최근 점수. 마지막 학습일 내림차순. 1차에서는 검색을 제공하지 않으며, 동작하지 않는 검색 아이콘도 두지 않는다.

책 카드 선택 → S2 바로 찍기 → S3 (책 미지정 상태로 시작) 카드 스와이프 → 책 삭제. 회차 전체 삭제 경고 후 확인 기록 없음 → 빈 상태 화면과 첫 촬영 버튼
GET /books · DELETE /books/{bookId}
S2

책 상세 · 회차 목록

상단에 책 제목, 회차 수, 총 글자 수. 회차 카드는 N회차, 요약 제목, 생성일, 퀴즈 응시 배지, 상태 배지. 회차 번호 오름차순. 요약이 없는 회차는 원문 앞부분을 대체 표기한다.

DONE → S8 PROCESSING → S7로 이동해 폴링 이어받기 FAILED → 재시도 확인 후 요약 재요청, S7로 이동 회차 추가 → S3 (해당 책으로 지정된 상태) 마지막 회차를 삭제해도 책은 유지. 회차 0으로 표시하고 직접 삭제 가능
GET /books/{bookId} · POST /documents/{id}/retry
S3

이미지 선택

촬영·갤러리 선택, 썸네일 순서 변경, 장수 표시(3 / 8). 책이 지정된 경우 상단에 대상 책을 노출한다. 페이지 순서가 곧 텍스트 순서다.

최대 8장. 초과 시 스낵바 안내 후 무시. 0장이면 추출 버튼 비활성 펼침면 촬영도 허용. 좌우 인식 순서 보정은 2차 과제 권한 거부 → 설정 이동 안내
S4

OCR 진행

기기 내 순차 처리. 장당 리사이즈(긴 변 1600px) 후 ML Kit 호출, 페이지 순서대로 병합.

100자 미만 → 재촬영 안내 후 S3 복귀. 서버 요청 없음 10,000자 초과 → 절단하고 S5에 안내 배너 취소 → S3 복귀. 처리 결과 폐기
S5

텍스트 확인 · 편집

추출 결과를 접힌 상태로 표시하고 편집 가능하게 한다. OCR 오류를 사용자가 직접 교정해 요약 품질을 확보하고, 불필요한 LLM 호출을 차단한다.

요약하기 · 책 지정됨 → 서버 전송 후 S7 요약하기 · 책 미지정 → S6 오프라인 → 요약하기 선택 시점에만 연결 확인. 편집 내용은 화면에 유지, 기기 임시 저장 없음
POST /documents → jobId
S6

책 선택 바로 찍기 경로만

기존 책 목록(최근 학습 순), 상단 고정 "새 책 만들기", 이름 필터. 필터는 같은 화면에서 목록을 좁히는 인라인 동작으로, 별도 결과 화면을 갖는 검색과 구분한다.

기존 책 선택 → 해당 책에 회차로 추가, S7 새 책 만들기 → 제목 입력 → 책 생성 후 S7. 제목이 비면 생성 버튼 비활성 같은 제목의 책을 막지 않는다 뒤로가기 → S5 복귀, 편집 텍스트 유지
GET /books · POST /books
S7

요약 생성 대기

2초 간격 상태 조회. 경과 시간 표시. DONE 수신 시 S8로 이동.

취소 → 화면만 벗어남. 서버 작업은 계속 진행되어 결과가 저장되고, 회차는 진행 중 상태로 목록에 나타남 FAILED → 사유 표시 후 재시도. S5 텍스트 유지 60초 초과 → 지연 안내로 전환하되 폴링 유지 앱 재실행 → 보관된 jobId로 상태 재조회해 복구
GET /jobs/{jobId} 반복
S8

요약 보기 허브

상단에 책 제목 · N회차. 제목, 핵심 항목(유형 라벨 + heading + detail), 용어 목록, 원문 접이식 영역. 유형은 좌측 색 스트라이프와 라벨 칩으로만 구분하고 본문에는 색을 적용하지 않는다.

퀴즈 풀기 → 최초 진입 시 생성 요청, 재진입 시 저장된 퀴즈 조회 후 S9 퀴즈 생성 대기는 화면 전환 없이 버튼 내에서 처리 책 제목 영역 선택 → S2 이전 응시 기록이 있으면 점수 배지와 결과 보기 진입점 노출
GET /documents/{id} · POST · GET /documents/{id}/quiz
S9

퀴즈 풀이

진행 표시(2 / 3), 4지선다, 이전·다음 이동, 마지막 문항에서 제출. 풀이 중 정답과 해설은 노출하지 않는다.

미응답 문항이 있으면 제출 시 확인 다이얼로그 이탈 시도 → 진행 소실 경고
S10

채점 결과

점수 요약(3문제 중 2문제 정답)과 문항별 카드. 선택한 답, 정답, 해설을 함께 표시하고 오답을 강조한다.

다시 풀기 → S9 재진입. 동일 문항, 결과는 누적 저장 요약으로 돌아가기 → S8
POST /quizzes/{quizId}/results

퀴즈 생성 대기 — 버튼 내 처리

퀴즈 생성도 LLM 호출이라 즉시 끝나지 않는다. 별도 대기 화면으로 전환하지 않고 S8에 머문 채 버튼 안에서 대기를 표현한다. 화면을 유지하므로 대기 중에도 요약을 열람할 수 있고, 재진입 시에는 기존 퀴즈를 반환받아 1초 이내에 전환된다.

단계처리버튼 상태
1버튼 선택, 생성 요청 전송비활성 + 스피너
2응답 200 — 기존 퀴즈 존재스피너 유지, 4단계로
3응답 202 — 2초 간격 상태 조회스피너 유지
4퀴즈 조회 완료원복 후 S9 전환

생성 실패 시 요약 화면을 유지한 채 버튼을 원복하고 스낵바로 재시도를 안내한다. 대기 중 이탈해도 서버 작업은 계속되며, 로컬에 보관한 jobId로 재진입 시 상태를 재조회한다. 진행 중 작업이 있으면(409) 반환된 jobId로 폴링을 이어받는다.

조정 대상. 생성 소요 시간이 10초를 초과하면 진행 문구를 추가하거나 대기 화면 전환 방식을 재검토한다.

동일 문항 반복은 복습 용도에 부합하며 무료 티어 소진을 억제한다. 문항 재생성이 필요해지면 별도 기능(문제 새로 뽑기)으로 분리해 검토한다.

05데이터 모델

이미지 테이블은 존재하지 않는다. 소유자 식별은 Book.userId로 하고 회차는 책을 통해 귀속된다.

Book        id, userId, title, createdAt
Document    id, bookId, sequence, extractedText, charCount, status, createdAt
Summary     id, documentId, contentJson
Quiz        id, documentId, questionsJson, createdAt
QuizResult  id, quizId, answersJson, score, solvedAt
필드설명
Book.userIdFirebase uid. 사용자 테이블은 두지 않는다. 재설치로 uid가 바뀌어 남는 데이터의 정리는 2차 과제
Book.title사용자가 입력. 책 이름은 사용자가 가장 정확히 알고 있으며 입력은 권당 한 번뿐이다
Document.sequence책 안에서의 등록 순서. 화면에는 3회차처럼 표기
Document.statusPROCESSING · DONE · FAILED. 실패한 회차도 목록에 남겨 재시도 경로를 제공

회차 제목 컬럼을 두지 않는다. 회차 제목은 Summary.contentJson의 title이 유일한 출처다. 같은 값을 두 곳에 저장하면 동기화 문제가 생긴다. 요약이 없는 회차(진행 중·실패)는 목록에서 원문 앞부분을 대체 표기한다.

QuizResult는 응시할 때마다 레코드를 누적 생성한다. 덮어쓰지 않으므로 학습 추이를 확인할 수 있다. 목록과 요약 화면 배지에는 가장 최근 점수를 표시한다.

비동기 작업 규약

LLM 호출이 포함된 요청(요약 생성, 퀴즈 생성)은 202 Accepted와 jobId를 반환한다.

요청 → 202 { jobId } → GET /jobs/{jobId} 반복 → DONE → 결과 조회

작업 취소 엔드포인트는 두지 않는다. 대기 화면의 취소는 화면 이탈만 의미하며 서버 작업은 계속 진행되어 결과가 저장된다. LLM 호출이 시작된 뒤에는 중단해도 비용이 절약되지 않고, 결과를 남기는 편이 재시도보다 낫다.

  └─ 앱 종료 · 이탈
       → 회차는 status FAILED 로 보관

핵심 항목 유형

내용의 성격을 여섯 가지로 분류한다. 화면에서는 유형별로 색과 라벨을 달리해 표시하며, 색은 앱 테마에서 가져오므로 다크 모드가 자동으로 대응된다.

type라벨성격
definition정의개념이 무엇인지
mechanism원리동작 방식, 절차, 흐름
cause원인무엇 때문에 발생하며 그로 인해 무엇이 일어나는지
comparison비교장단점, 다른 것과의 차이
caution주의함정, 혼동하기 쉬운 지점
example예시구체적인 사례로 든 설명

S8 표시 예

정의

프로세스의 정의

실행 중인 프로그램으로, 메모리에 적재되어 CPU를 할당받는 작업 단위.

원리

프로세스 상태 전이

생성·준비·실행·대기·종료 다섯 상태를 오가며 스케줄러가 전이를 관리한다.

결정이유
definition 중립색가장 빈번하게 등장하므로 시각적 부담을 낮추고 나머지 유형이 상대적으로 눈에 띄게 한다
cause 단일 유형교재 문장에서 인과는 한 덩어리로 서술되는 경우가 많다. 분리하면 결과 유형이 거의 쓰이지 않거나 한 인과 관계가 억지로 두 항목으로 쪼개진다
example 별도 유형개념 설명과 성격이 뚜렷이 다르고 분류가 쉬우며, 복습 시 사례만 다시 훑는 용도가 있다
마크다운 미사용색을 표현할 수 없고 LLM이 서식을 매번 다르게 적용해 화면 일관성이 무너진다. 유형은 데이터로 받고 표현은 앱이 결정한다
detail 순수 텍스트본문 내 용어 강조(emphasis)는 2차 과제. 1차에 넣으면 요약 품질 문제와 스키마 문제를 구분하기 어렵다

프롬프트 지시

· 원문에 없는 내용을 생성하지 말 것

· title은 해당 회차의 내용을 특정할 수 있게 구체적으로 작성할 것. 운영체제의 개념처럼 범위가 넓은 표현 대신 프로세스 상태 전이와 PCB처럼 다룬 대상을 드러낼 것

· 각 핵심 항목에 내용 성격에 맞는 type을 부여할 것. 분류가 애매하면 definition을 사용할 것

· detail에 마크다운 서식을 넣지 말 것

제목 품질이 목록에서의 탐색성을 좌우한다. 회차가 쌓였을 때 원하는 내용을 찾는 수단은 검색이 아니라 제목이므로, 검색 기능보다 우선한다.

서버 내부 처리

요약 — 텍스트 수신 → 정제(공백·줄바꿈 정리, 하이픈 분철 결합)
       → 목표 핵심 항목 수 산정 → LLM 호출 → 응답 검증(항목 수, 필수 필드)
       → Document + Summary 저장 → Job DONE

퀴즈 — 원문 + 요약 핵심 항목 조회 → 문항 수 결정(1차 3 고정)
       → LLM 호출 → 응답 검증(문항 수, 선택지 4개, answerIndex 범위)
       → Quiz 저장 → Job DONE

배포서버 레포 루트가 곧 빌드 루트. 경로 설정 불필요

배포 플랫폼 대부분이 루트 디렉터리 지정을 지원하므로 배포 자체는 모노레포에서도 가능하다. 분리의 실질적 이유는 저장소마다 역할과 문서를 분명히 하기 위해서다. 분리 비용은 API 스펙 변경 시 커밋이 두 저장소로 갈리는 점과 로컬 작업 시 두 디렉터리를 병행하는 점이며, 엔드포인트 규모가 작아 스펙 변동 빈도가 낮으므로 수용 가능한 수준으로 판단한다.

작업 방식과 품질 기준은 이 문서에 두지 않는다. 커밋 규칙, README 구성, 테스트 범위, 코드 구조, 네이밍, 환경 변수는 04_개발규약.md에서 다룬다. 기획서는 무엇을 만들지를, 규약 문서는 어떻게 작업할지를 담는다.

09설계 결정 근거

각 결정과 그 이유.

결정근거
책 > 회차 2단계한 권을 나눠 촬영하므로 평면 목록으로는 권 구분과 진도 파악이 불가능
책 제목 직접 입력사용자가 가장 정확히 알고 있으며 입력은 권당 한 번뿐
앱 내 OCR이미지 전송·저장을 제거해 저작권 부담 최소화, 서버 부하 감소
텍스트 확인 화면OCR 오류를 사용자가 교정해 요약 품질 확보, 불필요한 LLM 호출 차단
폴링 방식푸시 전달은 비보장. 포그라운드 대기 시나리오에 부적합
Spring BootKotlin 백엔드 표준 구성. 레이어 구조가 관례적이라 가독성 확보
요약·퀴즈 분리 호출요약 응답 지연 최소화, 미사용 퀴즈 생성 비용 제거
구조화 출력자유 텍스트 파싱 제거로 응답 처리 안정성 확보
핵심 항목 유형 데이터화표현을 앱이 결정해 화면 일관성과 테마 대응 확보
문항 수 1:1 연동요약과 퀴즈가 대응해 학습 점검 도구로 기능, 출제 범위 균등 분포
퀴즈 1세트 고정복습 용도에 부합, LLM 호출을 최초 1회로 제한
제목 컬럼 미보유같은 값의 중복 저장을 피하고 진실의 출처를 하나로 유지
실패 회차 보존추출·교정을 거친 텍스트를 살려 재촬영 없이 재시도
취소 API 미도입중단해도 비용이 절약되지 않고 이탈 처리와 규칙이 일치
검색 1차 미도입탐색 수단은 구체적인 회차 제목이 우선. 목록이 길어지는 S6에만 필터 제공
