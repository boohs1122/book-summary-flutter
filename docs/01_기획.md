# BookSummaryApp 기획

작성일: 2026-09-20
상태: 초안 (확정 스펙 반영)

## 1. 개요

책이나 텍스트가 담긴 이미지를 촬영하면 텍스트를 추출해 구조화된 요약을 만들고,
해당 내용을 바탕으로 객관식 퀴즈를 제공하는 개인 학습용 앱.

기록은 **책 > 회차** 두 단계로 묶는다. 한 권을 여러 번에 나눠 촬영하게 되므로
평면 목록으로는 권 구분과 진도 파악이 불가능하다.

- 클라이언트: Flutter
- 서버: Kotlin + Spring Boot
- 저장소 구성: 레포 2개 분리 (상세는 9장)

개인 학습용 앱이며 공개 저장소로 운영한다. 작업 방식과 품질 기준은
[04_개발규약.md](04_개발규약.md)에서 별도로 다룬다.

## 2. 핵심 흐름

```
홈(책 목록)
  ├─ [바로 찍기] ─────────────────────┐
  └─ 책 선택 → 책 상세(회차 목록)      │
                └─ [회차 추가] ────────┤
                                       ▼
                        카메라/갤러리 촬영(최대 8장)
                          → 앱 내 OCR(ML Kit)
                          → 인식 텍스트 확인·편집
                          → 책 선택 (바로 찍기 경로만)
                          → 서버 전송(텍스트만)
                          → LLM 요약 생성(비동기)
                          → 요약 조회
                          → 퀴즈 생성 → 풀이 → 채점·해설
```

책 상세에서 시작하면 대상 책이 이미 정해져 있으므로 책 선택 단계를 건너뛴다.

| 요약 실패 복구 | 실패 문서를 목록에 남기고 재시도 제공 |
| 오프라인 | OCR·편집은 동작. 전송 시점에만 연결 확인 후 안내 |

### 3.1 분량 연동 규칙 (확장 시)

퀴즈 문항 수는 요약 핵심 항목 수와 1:1로 대응시킨다. 서버가 글자 수로
목표 핵심 항목 수를 산정해 요약 프롬프트에 전달하고, 생성된 핵심 항목
개수를 그대로 문항 수로 사용한다.

| 텍스트 길이 | 핵심 항목 | 퀴즈 문항 |
|---|---|---|
| ~1,500자 | 3 | 3 |
| 1,500~4,000자 | 4 | 4 |
| 4,000~7,000자 | 5 | 5 |
| 7,000자~ | 6 | 6 |

요약과 퀴즈가 대응해 학습 점검 도구로 기능하며, 출제 범위가 문서 전체에
고르게 분포한다. 상한을 6으로 두어 출력 토큰과 풀이 시간을 제한한다.

1차 구현은 3문제 고정. 요약 품질이 안정된 뒤 연동 방식으로 확장한다.

문항 수는 서버에서 계산해 프롬프트에 숫자로 전달하고, 구조화 출력
스키마에서 배열 길이를 강제한다. 응답의 실제 개수가 요청과 다를 경우
부족하면 재요청, 초과하면 절단한다.

핵심 항목의 `type`이 정의된 여섯 값에 해당하지 않으면 `definition`으로
치환한다. LLM이 스키마에 없는 값을 생성할 수 있으므로 서버에서 방어한다.

## 4. 데이터 모델

```
Book        id, userId, title, createdAt
Document    id, bookId, sequence, extractedText, charCount, status, createdAt
Summary     id, documentId, contentJson
Quiz        id, documentId, questionsJson, createdAt
QuizResult  id, quizId, answersJson, score, solvedAt
```

사용자 테이블은 두지 않는다. Firebase `uid`를 `Book.userId`에 저장하는 것으로
소유자 식별이 충분하다. 익명 로그인은 재설치 시 uid가 바뀌어 이전 데이터가
주인 없이 남는다. 이 데이터의 정리는 1차 범위에서 제외하고 8장에서 관리한다.

`Book.title`은 사용자가 입력한다. 책 이름은 사용자가 가장 정확히 알고 있으며
입력은 권당 한 번뿐이다.

`Document.sequence`는 책 안에서의 등록 순서다. 화면에는 `3회차`처럼 표기한다.
소유자 식별은 `Book.userId`로 하고 `Document`는 책을 통해 귀속된다.

`Document.status`는 `PROCESSING` · `DONE` · `FAILED` 중 하나다. 실패한 문서도
목록에 남겨 재시도 경로를 제공한다.

문서 제목은 `Document`에 두지 않고 `Summary.contentJson`의 `title`을 사용한다.
같은 값을 두 곳에 저장하면 동기화 문제가 생기므로 진실의 출처를 하나로 유지한다.
요약이 없는 문서(진행 중·실패)는 제목이 없으며, 목록에서는 원문 앞부분을
대체 표기로 사용한다.

`QuizResult`는 응시할 때마다 레코드를 누적 생성한다. 덮어쓰지 않으므로 학습
추이를 확인할 수 있으며, 목록과 요약 화면 배지에는 가장 최근 점수를 표시한다.

## 5. LLM 출력 스키마

### 요약

```json
{
  "title": "한 문장 요약",
  "keyPoints": [
    {
      "type": "definition",
      "heading": "핵심 개념명",
      "detail": "1~2문장 설명"
    }
  ],
  "terms": [
    { "term": "용어", "meaning": "짧은 정의" }
  ]
}
```

#### 핵심 항목 유형

내용의 성격을 여섯 가지로 분류한다. 화면에서는 유형별로 색과 라벨을 달리해
표시하며, 색은 앱 테마에서 가져오므로 다크 모드가 자동으로 대응된다.

| `type` | 라벨 | 성격 |
|---|---|---|
| `definition` | 정의 | 개념이 무엇인지 |
| `mechanism` | 원리 | 동작 방식, 절차, 흐름 |
| `cause` | 원인 | 무엇 때문에 발생하며 그로 인해 무엇이 일어나는지 |
| `comparison` | 비교 | 장단점, 다른 것과의 차이 |
| `caution` | 주의 | 함정, 혼동하기 쉬운 지점 |
| `example` | 예시 | 구체적인 사례로 든 설명 |

`definition`은 가장 빈번하게 등장하므로 화면에서 중립색을 배정해 시각적
부담을 낮춘다. 나머지 유형이 상대적으로 눈에 띄도록 한다.

원인과 결과를 분리하지 않고 `cause` 하나로 둔다. 교재 문장에서 인과는 한
덩어리로 서술되는 경우가 많아, 분리하면 결과 유형이 거의 쓰이지 않거나
LLM이 한 인과 관계를 억지로 두 항목으로 쪼갠다.

`example`을 두는 이유는 예시가 개념 설명과 성격이 뚜렷이 다르고 분류가
쉬우며, 복습 시 사례만 다시 훑는 용도가 있기 때문이다.

마크다운을 쓰지 않는 이유는 두 가지다. 색을 표현할 수 없고, LLM이 서식을
매번 다르게 적용해 화면 일관성이 무너진다. 유형을 데이터로 받고 표현은
앱이 결정하는 방식이 일관성과 테마 대응 모두에서 낫다.

`detail`은 순수 텍스트로 받는다. 본문 내 용어 강조(`emphasis`)는 2차 과제로 둔다.
1차에 함께 넣으면 스키마가 무거워져 요약 품질 문제와 스키마 문제를 구분하기 어렵다.

### 퀴즈

```json
{
  "questions": [
    {
      "question": "문항",
      "options": ["...", "...", "...", "..."],
      "answerIndex": 2,
      "explanation": "해설"
    }
  ]
}
```

두 응답 모두 구조화 출력(JSON 스키마 강제)으로 받는다.

프롬프트에 포함할 지시는 다음과 같다.

- 원문에 없는 내용을 생성하지 말 것
- `title`은 해당 회차의 내용을 특정할 수 있게 구체적으로 작성할 것.
  `운영체제의 개념`처럼 범위가 넓은 표현 대신 `프로세스 상태 전이와 PCB`처럼
  다룬 대상을 드러낼 것
- 각 핵심 항목에 내용 성격에 맞는 `type`을 부여할 것. 분류가 애매하면
  `definition`을 사용할 것
- `detail`에 마크다운 서식을 넣지 말 것

제목 품질이 목록에서의 탐색성을 좌우한다. 회차가 쌓였을 때 원하는 내용을
찾는 수단은 검색이 아니라 제목이므로, 검색 기능보다 우선한다.

## 6. LLM 선정

1차 후보는 Google Gemini API 무료 티어. 무료 티어는 입력 데이터가 모델 개선에
활용될 수 있으므로, 외부 공유 기능은 두지 않고 개인 학습 용도로 한정한다.
무료 한도 초과 또는 품질 문제 발생 시 유료 API로 전환한다.

## 7. 저작권 처리

- 촬영 이미지는 서버로 전송하지 않으며 저장하지 않는다.
- 추출 텍스트는 개인 학습 목적으로만 보관한다.
- 공유·배포 기능은 제공하지 않는다.

## 8. 미결정 사항

- 실기기 검증 후 화면 레이아웃·문구 개선
- 요약·퀴즈 프롬프트 품질 개선
- 요청 한도 정책 (사용자당 일일 요약 생성 횟수)
- 목록 페이지네이션 크기
- 검색 도입 시점과 범위 (아래 2차 설계안 참고)
- 본문 내 용어 강조 (`emphasis`) 도입 시점
- 책 단위 통합 퀴즈 (여러 회차를 묶어 출제)
- 책 병합 기능
- 회차 순서 변경 허용 여부
- 푸시 알림 도입 시점
- 계정 연결(Google 로그인) 도입 시점. 익명 uid를 유지한 채 연결해 재설치 후 복구
- 비활성 사용자 데이터 정리. 도입 시 `User(id, createdAt, lastSeenAt)`를 추가하고 `lastSeenAt` 기준 일정 기간 비활성 사용자의 데이터를 일괄 삭제
- 펼침면 좌우 인식 순서 보정 (블록 좌표 기반 재정렬)

### 검색 2차 설계안

1차에서는 도입하지 않는다. 회차가 쌓여 목록 탐색이 어려워지면 아래 형태로 추가한다.

| 항목 | 내용 |
|---|---|
| 위치 | 홈 상단 고정 검색창 (M3 Search bar). 앱바 아이콘 방식은 발견성이 낮음 |
| 결과 화면 | 전용 화면. 책 / 회차 두 섹션으로 구분 |
| 결과 표기 | 회차 결과에는 반드시 책 이름을 함께 표기하고 매치 문구를 잘라 노출 |
| 검색 범위 | 책 제목 + 요약 제목·핵심 항목·용어 |
| 제외 | 원문 전문 검색 — 전문 검색 인덱스가 필요해 DB 설계에 영향을 주며, OCR 오타로 품질이 불안정 |
| API | `GET /search?q=` 신규 |

책 상세 안의 검색과 요약 화면의 원문 검색은 넣지 않는다. 전자는 회차 20개
이상에서만 의미가 있고, 후자는 우선순위가 낮다.

### 개발 후 실측으로 조정할 값

아래 값은 실제 촬영물로 테스트한 뒤 확정한다.

| 값 | 현재 | 조정 관점 |
|---|---|---|
| 최대 장수 | 8장 | OCR 처리 시간, 확인 화면 가독성 |
| 텍스트 상한 | 10,000자 | 요약 밀도, LLM 입력 토큰 |
| OCR 실패 기준 | 100자 | 오탐·미탐 비율 |
| 핵심 항목 구간 | 3~6개 | 요약 결과 체감 밀도 |
| 퀴즈 대기 방식 | 버튼 내 | 생성 소요 시간 10초 초과 여부 |
| 항목 유형 분포 | 6종 | 실제 요약에서 유형별 비율. 5% 미만인 유형은 통합 검토 |
| 펼침면 보정 | 미적용 | 좌우 페이지 인식 순서 오류 발생 빈도 |

### 분리 근거

| 관점 | 내용 |

| 언어 통계 | 레포별 단일 언어로 표시되어 저장소 성격이 즉시 드러남 |
| 독립성 | 앱·서버를 각각 독립적으로 버전 관리·배포 가능 |
| README | 독자가 달라 문서를 각각의 목적에 맞게 구성 |
| 배포 | 서버 레포 루트가 곧 빌드 루트. 경로 설정 불필요 |

배포 플랫폼 대부분이 루트 디렉터리 지정을 지원하므로 배포 자체는
모노레포에서도 가능하다. 분리의 실질적 이유는 저장소마다 역할과 문서를 분명히 하기 위해서다.

### 분리에 따른 비용

- 로컬 작업 시 두 디렉터리를 병행

엔드포인트 규모가 작아 스펙 변동 빈도가 낮으므로 수용 가능한 수준으로 판단한다.

### 구현 보완 상세 계획

기존 확정 스펙과 화면 흐름의 미구현 항목을 보완한다. 아래 항목은 모두 미완료이며,

#### 1. 회차 개별 삭제

- [ ] 책 상세의 회차 카드에 스와이프 삭제와 확인 다이얼로그를 제공한다. 해당 회차의 요약·퀴즈·풀이 기록도 삭제됨을 안내한다.
- [ ] 앱 repository·provider에 E5 호출을 추가하고 삭제 중 중복 요청을 차단한다. 실패 시 카드를 유지하고 안내·재시도를 제공한다.
- [ ] 성공 시 책 목록·책 상세의 회차 수·총 글자 수·최근 점수를 다시 조회하고 삭제된 회차의 조회 상태와 관련 로컬 작업 정보를 정리한다.
- [ ] 마지막 회차를 삭제해도 책은 유지하고 빈 상태와 회차 추가 버튼을 표시한다.
- [ ] 완료·실패·생성 중 회차 삭제, 실패 후 재시도, 마지막 회차 삭제를 검증한다. 생성 중 삭제 후 결과가 다시 나타나지 않는지는 서버 연동으로 확인한다.

완료 기준: 선택한 회차만 삭제되며 다른 회차는 유지되고 관련 집계와 작업 복구 목록에 삭제 결과가 반영된다.

#### 2. 요약 화면의 최근 점수와 이전 결과 보기

- [ ] E4의 퀴즈 존재 여부·식별자·최근 점수를 앱 모델에 반영하고 요약 화면에 최근 점수 배지를 표시한다.
- [ ] 응시 이력에 따라 버튼을 '퀴즈 풀기' 또는 '다시 풀기'로 표시한다. 재응시는 저장된 동일 문항을 사용한다.
- [ ] 이전 결과 조회 API의 존재 여부를 서버에서 확인한다. 없으면 소유권 검증과 최신 응시 결과 반환 계약을 정의하고 서버·앱을 함께 구현한다.
- [ ] 결과 보기에서 저장된 최신 응시의 선택 답·정답·해설을 표시한다. 점수만으로 결과를 복원하거나 결과 조회가 새 응시 기록을 만들지 않도록 한다.
- [ ] 채점 후 책 목록·책 상세·요약의 관련 조회 상태를 갱신한다.
- [ ] 미응시·첫 응시·재응시·앱 재실행 후 결과 조회와 조회 실패 후 재시도를 검증한다.

완료 기준: 최신 점수와 결과가 화면 간 일치하고 앱 재실행 후에도 마지막 결과를 열 수 있으며 열람만으로 응시 기록이 추가되지 않는다.

#### 3. 촬영 권한 거절 안내

- [ ] 카메라·사진 접근 권한 거절과 일반 이미지 선택 오류를 구분한다. 플랫폼의 시스템 사진 선택 방식에 따라 불필요한 권한을 요청하지 않는다.
- [ ] 권한 거절 시 필요한 권한과 설정 이동 방법을 다이얼로그로 안내하고 설정 열기·취소 액션을 제공한다.
- [ ] 설정에서 복귀하면 촬영·선택을 다시 시도할 수 있게 하고 기존 선택 이미지를 유지한다.
- [ ] Android·iOS 실기기에서 최초 거절, 반복 거절, 설정에서 허용 후 복귀, 선택 취소를 확인한다.

완료 기준: 권한 거절 후 화면이 유지되고 설정 변경 후 재설치 없이 촬영·선택을 재개할 수 있다.

#### 4. 진행 중 회차와 작업의 정확한 연결

- [ ] 책 상세에서 같은 책의 첫 로컬 작업을 선택하는 로직을 제거하고 선택한 회차의 식별자와 작업 식별자로 연결한다.
- [ ] 서버 응답을 확인하고 진행 중 회차의 jobId를 얻을 수 있는 계약을 정한다. 필요한 응답 필드나 조회 API는 명세에 반영한다.
- [ ] 로컬 보관 작업에도 확인된 documentId를 연결하고 기존 저장 데이터의 필드 누락을 처리한다. 제출 직후 documentId가 없는 단계는 별도로 처리한다.
- [ ] 로컬 정보가 없거나 작업이 만료되면 서버의 회차 상태를 다시 확인하고 완료·실패·진행 중에 맞는 안내와 이동 경로를 제공한다.
- [ ] 같은 책의 두 작업, 서로 다른 책의 작업, 앱 재실행, 로컬 정보 누락·작업 만료를 검증한다.

완료 기준: 선택한 회차의 작업만 이어받고 다른 회차 결과로 이동하지 않으며 작업 정보를 찾지 못해도 복구 가능한 안내를 제공한다.

#### 5. 회차 관련 화면의 책 제목 표시

- [ ] 이미지 선택·OCR 진행·텍스트 확인·요약 대기·퀴즈 풀이·채점 결과의 책 제목 표시를 점검하고 누락된 화면을 보완한다.
- [ ] 대상 책이 정해진 경로에서는 책 제목을 표시하고 홈에서 바로 촬영한 경로는 책 선택 전까지 제목 표시를 생략한다.
- [ ] 제목 조회 중·실패 상태가 기기 내 OCR·편집을 막지 않게 한다. 오프라인에서는 이미 확보한 제목을 활용한다.
- [ ] 제목 수정 후 재진입, 긴 제목, 오프라인 OCR·편집, 책 상세에서 시작한 흐름을 검증한다.

완료 기준: 책이 지정된 회차 흐름에서 대상 책을 확인할 수 있고 제목 변경이 반영되며 오프라인 기기 내 처리가 유지된다.
